# ۰. دستورالعمل الزام‌آور برای Codex

این سند مبنای کار است. قبل از هرگونه تغییر کد، مخزن فعلی را بررسی کن و گزارش فنی بساز. سپس طبق فازهای این سند کار کن.

1. مخزن فعال پروژه همان Fork کاربر است؛ هیچ‌گاه به‌جای آن مخزن بالادستی را کلون یا تغییر نده.
2. ابتدا ساختار کل پروژه، شاخه فعلی، آخرین commit، فایل‌های تنظیمات، migrationها، تست‌ها، Docker و تمام Git Submoduleها را بررسی کن.
3. اجرای `git submodule status` و در صورت نیاز `git submodule update --init --recursive` را بررسی کن. قبل از تغییر submoduleها، وضعیت موجود و commitهای pin‌شده را ثبت کن.
4. معماری فعلی Django، مدل‌های Game/GameVersion/InteractionCard/Player/Session/StateVariable، کتابخانه کارت‌ها، گراف Activity Map و موتور Django Dialog Engine را حفظ و توسعه بده؛ مگر آنکه با شواهد و تست ثابت شود بخشی قابل استفاده نیست.
5. قبل از افزودن مدل یا موتور جدید، بررسی کن آیا مفهوم آن از قبل در مدل‌های فعلی وجود دارد. از ایجاد دو سیستم موازی برای بازی، مرحله، نشست، متغیر، کارت یا اجرای منطق خودداری کن.
6. تمام قابلیت‌های موجود و سالم باید پس از تغییرات کار کنند. تغییرات باید با migrationهای افزایشی و سازگار انجام شوند؛ حذف یا بازنویسی داده‌های موجود ممنوع است.
7. فارسی‌سازی باید از طریق سیستم ترجمه و فایل‌های locale انجام شود؛ متن‌های نمایشی را از منطق برنامه جدا نگه دار. نام کلاس‌ها، فیلدها، شناسه کارت‌ها، کلیدهای JSON، APIها و نام‌های داخلی را بی‌دلیل فارسی نکن.
8. تمام رابط‌های نمایشی کاربران و مدیران باید فارسی و RTL شوند. چیدمان باید در موبایل و دسکتاپ درست باشد. متن و محتوای ثبت‌شده توسط مدیر نیز باید امکان فارسی داشته باشد.
9. هیچ عملیات مهمی صرفاً نمایشی یا Mock نباشد. فرم، دکمه، جست‌وجو، ذخیره، انتشار، ورود، ابزار و گزارش باید به منطق واقعی متصل باشند.
10. منبع حقیقت وضعیت بازی، پاسخ صحیح، پیشرفت، مسیر بعدی و امتیاز، سرور است. کلاینت حق ندارد با ارسال `completed=true` یا امتیاز دلخواه مرحله را تکمیل کند.
11. هر فاز را مستقل پیاده‌سازی کن؛ پس از هر فاز تست واحد، تست یکپارچه و تست دستی قابل تکرار اجرا کن. بدون قبولی تست‌ها به فاز بعد نرو.
12. از تغییر فناوری اصلی پروژه (Django، Dialog Engine، پایگاه داده و معماری فعلی) فقط برای سلیقه شخصی خودداری کن. اگر تغییری ضروری است، قبل از اجرا دلیل، هزینه، مهاجرت و ریسک آن را مستند کن.
13. اسرار، توکن‌ها، کلیدهای پیام‌رسانی و رمزهای پایگاه داده نباید در Git ثبت شوند. فایل `.env.example` بدون مقدار محرمانه ارائه شود.
14. هر قابلیت جدید باید مستند، قابل تنظیم، قابل تست و قابل خاموش/روشن شدن باشد.
15. در پایان هر فاز، خلاصه تغییرات، فایل‌های تغییرکرده، migrationها، دستورهای اجرا و نتیجه تست‌ها را به فارسی گزارش کن.

# ۱. معرفی محصول

## ۱.۱ چشم‌انداز

تبدیل Hive Mechanic به یک پلتفرم چندشهری و چندبازی که در آن:

- مدیر کل سامانه شهرها و بازی‌ها را مدیریت می‌کند.
- طراح بازی از طریق پنل، هر بازی را مرحله‌به‌مرحله می‌سازد.
- طراح می‌تواند از کتابخانه ابزارها و کارت‌های تعامل، ابزار دلخواه را به هر مرحله اضافه و تنظیم کند.
- موتور فعلی و توسعه‌یافته Hive Mechanic روی سرور، تعریف بازی را اجرا و تمام تصمیم‌های مهم را اعتبارسنجی می‌کند.
- کاربر ثبت‌نام می‌کند، ابتدا شهرهای دارای بازی فعال را می‌بیند، شهر را انتخاب می‌کند و سپس بازی‌های آن شهر را مشاهده و اجرا می‌کند.
- بازی‌ها می‌توانند داستانی، معمایی، گنج‌یابی، گردشگری، تاریخی، رقابتی، GPSمحور، QRمحور یا ترکیبی باشند.

## ۱.۲ اهداف اصلی

- حفظ ارزش و قابلیت‌های Hive Mechanic و توسعه روی همان مخزن.
- افزودن ساختار چندشهری؛ هر شهر می‌تواند چندین بازی مستقل داشته باشد.
- تبدیل Builder موجود به محیط طراحی کامل، فارسی و قابل استفاده برای مدیر غیر فنی.
- حفظ موتور اجرا در سمت سرور و استفاده از Dialog Engine و معماری کارت‌های تعاملی موجود تا حد ممکن.
- ایجاد تجربه کاربری مستقل و نصب‌پذیر PWA برای بازیکنان.
- افزودن ابزارهای واقعی مبتنی بر قابلیت‌های موبایل و مکان واقعی.
- امکان افزودن ابزارهای جدید به‌صورت ماژولار بدون بازنویسی هسته موتور.
- حفظ نسخه‌های منتشرشده و نشست‌های فعال هنگام تغییر بازی.

## ۱.۳ اصول طراحی

1. **Server authoritative:** سرور مرجع نهایی وضعیت، قوانین، اعتبارسنجی و امتیاز است.
2. **Data-driven authoring:** ساخت بازی جدید باید از طریق داده و Builder انجام شود، نه کدنویسی اختصاصی.
3. **Reuse first:** ابتدا کارت‌ها، مدل‌ها، Dialog Engine، گراف و سیستم نشست فعلی بررسی و استفاده شوند.
4. **No destructive migration:** هیچ داده موجودی حذف یا بی‌صدا بازنویسی نشود.
5. **Modular cards/tools:** هر ابزار قرارداد مشخص، تنظیمات، رابط کاربری و اعتبارسنج سمت سرور دارد.
6. **Mobile first:** محیط بازیکن ابتدا برای موبایل طراحی می‌شود.
7. **Privacy by design:** مکان و رسانه فقط با رضایت و در زمان نیاز بازی دریافت شوند.

# ۲. ارزیابی مبنای فعلی مخزن و راهبرد توسعه

این بخش بر اساس بررسی Fork عمومی کاربر در تاریخ سند تهیه شده است. Codex باید در فاز صفر آن را با نسخه‌ای که روی کامپیوتر کاربر Clone شده تطبیق دهد.

## ۲.۱ اجزای مشاهده‌شده در مخزن

| مسیر / جزء | نقش فعلی مشاهده‌شده | تصمیم توسعه |
|---|---|---|
| `builder/` | مدل‌ها، پنل Builder، فعالیت‌ها، کارت‌ها، نشست‌ها، رسانه، کاربران و مدیریت محتوا | حفظ و توسعه؛ نقطه اصلی پنل مدیر |
| `builder/static/builder-js/` | رابط جاوااسکریپت Builder و فایل‌های Cytoscape و layout | حفظ گراف فعلی و ارتقای تجربه طراحی |
| `builder/templates/` | صفحات فعالیت‌ها، رسانه، بازیکنان، نشست‌ها، مدیریت و تنظیمات | فارسی‌سازی، RTL و توسعه صفحات |
| `activity_logger/` | ثبت فعالیت‌ها و رویدادها | حفظ و تکمیل گزارش رویدادهای بازی |
| `integrations/` | اتصال بازی به کانال‌ها و سرویس‌های بیرونی | حفظ؛ افزودن/تکمیل کانال وب/PWA در صورت نبود مسیر مناسب |
| `user_creation/` | جریان ایجاد حساب/درخواست دسترسی و شروط کاربر | بررسی و اتصال امن به حساب کاربری بازیکن |
| `hivemechanic/` | تنظیمات، URLها، WSGI و پیکربندی Django | حفظ معماری؛ تنظیم محیط تولید و فارسی‌سازی |
| `django_dialog_engine` | Git Submodule موتور دیالوگ و انتقال حالت | هسته اجرای بازی؛ حفظ و توسعه کنترل‌شده |
| `docker/` | Compose، Django، Nginx، cron و volumeها | مبنای استقرار؛ تکمیل تنظیم پایگاه داده تولید |
| `simple_messaging_*` | کانال‌های پیام‌رسانی مانند Twilio، Azure و Loopback | حفظ به‌عنوان کانال‌های مکمل، نه جایگزین PWA |

## ۲.۲ مدل‌های کلیدی موجود که باید حفظ شوند

بررسی `builder/models.py` وجود این مفاهیم را نشان می‌دهد:

- `Game`: دارای نام، slug، کارت‌های مرتبط، وضعیت/متادیتا، ویرایشگران و مشاهده‌کنندگان و قابلیت آرشیو.
- `GameVersion`: نگهداری تعریف JSON بازی، نقشه گراف Cytoscape و سازنده نسخه.
- `InteractionCard`: دارای شناسه، دسته‌بندی، توضیح، فعال/غیرفعال بودن، منطق ورود/ارزیابی، پیاده‌سازی سمت کلاینت، metadata، نسخه و امکان دریافت به‌روزرسانی از مخزن کارت.
- `Player`: شناسه بازیکن و متغیرهای سطح بازیکن.
- `Session`: اتصال بازیکن به نسخه بازی و وضعیت نشست.
- `StateVariable`: ذخیره وضعیت در سطح بازیکن، بازی یا نشست.
- `DataProcessor`: اتصال به داده/API بیرونی و ثبت لاگ پردازش.

این مدل‌ها باید مبنای توسعه باشند. مدل جدید فقط زمانی ساخته شود که یک نیاز مستقل و فاقد معادل واقعی در سامانه وجود داشته باشد.

## ۲.۳ قابلیت‌های موجود که نباید دوباره ساخته شوند

- سیستم بازی/فعالیت و نسخه بازی.
- کارت‌های تعاملی و دسته‌بندی کارت‌ها.
- مخزن کارت و امکان فعال‌سازی کارت‌ها.
- گراف/نقشه فعالیت و نمایش ارتباط گره‌ها.
- اجرای منطق دیالوگ و انتقال بین حالت‌ها در موتور موجود.
- نشست بازیکن و متغیرهای وضعیت.
- ثبت رویداد و گزارش فعالیت.
- مدیریت رسانه، بازیکن و نشست.
- سیستم‌های یکپارچه‌سازی و پیام‌رسانی.
- زیرساخت Docker موجود.

| امتیاز و تیم | متغیرها و تعاملات وجود دارند | بررسی سیستم امتیاز/تیم فعلی؛ فقط شکاف واقعی را توسعه بده |

## ۲.۵ نکات فنی مهم مخزن

- پروژه Django و Python است؛ آن را بدون دلیل به NestJS/Node.js یا معماری دیگر تبدیل نکن.
- `.gitmodules` چندین submodule را تعریف می‌کند؛ کپی‌کردن دستی یا حذف آن‌ها ممنوع است.
- فایل‌های Docker شامل سرویس‌های Django، Nginx و cron و volumeهای پایدار هستند.
- پیکربندی Docker در صورت تنظیم `PG_DB` می‌تواند به PostgreSQL متصل شود؛ در غیر این صورت فایل تنظیمات Docker از SpatiaLite استفاده می‌کند. برای استقرار تولیدی و قابلیت مکانی چندشهری، PostgreSQL با PostGIS باید مسیر ترجیحی و مستند باشد.
- فایل تنظیمات پایه شامل مقادیر قدیمی و پیش‌فرض‌های توسعه است؛ هیچ Secret یا `DEBUG=True` نباید در محیط عمومی استفاده شود.
- README فعلی مخزن بخشی از روش نصب قدیمی را نشان می‌دهد؛ دستورالعمل نصب واقعی باید بر اساس Docker و submoduleهای فعلی بازبینی شود.

| Super Admin | دسترسی کامل به تنظیمات، شهرها، بازی‌ها، کاربران، کارت‌ها، انتشار و گزارش‌ها |
| Admin | مدیریت سامانه طبق مجوزهای اعطاشده |
| City Manager | مدیریت شهرها و بازی‌های اختصاص‌یافته |
| Game Designer / Editor | ساخت و ویرایش بازی و مراحل؛ انتشار فقط با مجوز صریح |
| Tester | اجرای نسخه آزمایشی و ثبت اشکال، بدون دسترسی به پاسخ محرمانه |
| Support | مشاهده محدود حساب و نشست برای پشتیبانی؛ بدون تغییر غیرمجاز امتیاز |
| Player | مشاهده شهرها، انتخاب بازی و اجرای بازی‌های مجاز |

## ۳.۲ قواعد مجوز

- از Group/Permissionهای Django و نقش‌های موجود Hive استفاده کن؛ سیستم احراز مجوز موازی نساز.
- مجوزها باید هم عملیاتی و هم دامنه‌ای باشند؛ مثلاً City Manager فقط شهرهای تخصیص‌یافته را مدیریت کند.
- UI تنها گزینه‌های مجاز را نمایش دهد، اما کنترل نهایی همیشه در سمت سرور باشد.
- ایجاد/ویرایش/حذف/انتشار بازی، تغییر کارت‌ها، تغییر امتیاز و مدیریت کاربران در Audit Log ثبت شود.
- فقط نقش فنی مورد اعتماد اجازه نصب/ویرایش کد اجرایی InteractionCard را داشته باشد؛ طراح عادی فقط کارت نصب‌شده را انتخاب و تنظیم کند.

# ۴. معماری هدف

## ۴.۱ نمای کلی

معماری در چهار لایه منطقی پیاده‌سازی می‌شود:

1. **پنل مدیریت و Game Builder:** مدیریت شهر، بازی، گراف مراحل، کارت‌ها، رسانه و انتشار.
2. **موتور اجرای بازی سمت سرور:** Django Backend به‌همراه GameVersion، Session و Django Dialog Engine برای پردازش رویدادها و انتقال حالت.
3. **اپلیکیشن بازیکن (PWA):** رابط موبایل برای مشاهده شهرها، انتخاب بازی، نمایش مرحله و استفاده از GPS، نقشه، QR و قطب‌نما.
4. **لایه داده:** PostgreSQL و PostGIS برای داده‌های مکانی، کاربران، نسخه‌ها، نشست‌ها، وضعیت‌ها، رویدادها و امتیازها.

هر سه لایه کاربردی از API و لایه مجوز مشترک استفاده می‌کنند؛ هیچ منطق تعیین‌کننده بازی در PWA اجرا نمی‌شود.

## ۴.۲ تفکیک محیط‌ها

- **پنل مدیریت:** محیط امن برای مدیران و طراحان؛ شامل شهرها، کاتالوگ بازی‌ها، Builder، کارت‌ها، رسانه، کاربران، نشست‌ها، گزارش‌ها و تنظیمات.
- **اپ بازیکن:** مسیر و رابط مستقل و موبایل‌محور؛ ورود، انتخاب شهر، انتخاب بازی، معرفی بازی، اجرای مراحل، ابزارهای دستگاه و نتیجه.
- **موتور بازی:** سمت سرور؛ تفسیر تعریف بازی، مدیریت نشست، اجرای Dialog، ارزیابی شروط، پردازش رویداد، هینت و امتیاز.
- **کتابخانه کارت‌ها:** registry قابل توسعه از InteractionCardهای تأییدشده، همراه با schema و نسخه.

## ۴.۳ اصل حفظ موتور فعلی

موتور جدید موازی ایجاد نکن. جریان اجرای وب/PWA باید از همان منطق سمت سرور و مسیرهای موجود Session/GameVersion/Dialog Engine استفاده کند. اگر API فعلی برای ورودی مرورگر کافی نیست، یک adapter یا Integration وب اضافه کن که رویدادهای HTTP را به مسیر پردازش معتبر موجود تحویل دهد. منطق بازی را در کد UI پیاده‌سازی نکن.

# ۵. نیازمندی‌های تجربه بازیکن

## ۵.۱ ثبت‌نام و ورود

- بازیکن باید بتواند حساب پایدار ایجاد کند و وارد شود.
- روش پایه ورود در MVP: شماره موبایل و OTP از طریق provider قابل پیکربندی؛ در محیط توسعه، provider آزمایشی فقط برای توسعه باشد.
- معماری برای اتصال Google و Telegram در آینده آماده باشد؛ این دو برای MVP اجباری نیستند.
- پروفایل شامل شناسه یکتا، نام نمایشی، نام کاربری اختیاری، تصویر اختیاری، زبان و تنظیمات حریم خصوصی باشد.
- حساب کاربری Django باید بدون شکستن مدل Player فعلی به Player متصل شود؛ ترجیحاً با FK/جدول پیوند امن و migration سازگار.
- شناسه Playerهای قدیمی مرتبط با پیامک/کانال‌ها حفظ شود؛ حساب وب نباید هویت‌های قبلی را حذف یا بازنویسی کند.
- خروج از حساب و لغو نشست‌های فعال پشتیبانی شود.

## ۵.۲ ترتیب اجباری نمایش شهر و بازی

این ترتیب بخشی از منطق محصول است و نباید معکوس شود:

1. کاربر وارد حساب می‌شود.
2. صفحه «انتخاب شهر» را می‌بیند.
3. فقط شهرهایی نمایش داده می‌شوند که حداقل یک بازی Published، فعال و قابل دسترسی دارند.
4. پس از انتخاب شهر، فهرست بازی‌های همان شهر نمایش داده می‌شود.
5. پیش از انتخاب شهر، فهرست کامل بازی‌ها نباید به کاربر نمایش داده شود؛ جست‌وجوی سراسری در نسخه اول مجاز نیست.

### اطلاعات کارت شهر

- نام شهر، کشور و استان/منطقه.
- تصویر و معرفی کوتاه.
- تعداد بازی‌های فعال.
- مرکز جغرافیایی و در صورت نیاز محدوده شهر.
- امکان جست‌وجو و فیلتر کشور/استان.
- نمایش نقشه و شهرهای نزدیک به‌صورت قابلیت اختیاری و فقط با مجوز مکان.

## ۵.۳ صفحه بازی‌های شهر

هر کارت بازی شامل:

- عنوان، پوستر، توضیح کوتاه و دسته‌بندی.
- سطح دشواری و زمان تقریبی.
- تعداد مراحل یا مأموریت‌ها در صورت قابل نمایش بودن.
- انفرادی/گروهی بودن و تعداد بازیکنان.
- وضعیت رایگان/پولی (پرداخت در نسخه اول خارج از دامنه است؛ فیلد برای آینده قابل نگهداری باشد).
- محدوده جغرافیایی و هشدارهای مهم.
- وضعیت دسترسی و تاریخ اعتبار بازی.

فیلترها: جدیدترین، محبوب، انفرادی، گروهی، دشواری، رایگان و دسته‌بندی.

## ۵.۴ صفحه معرفی و قوانین بازی

پیش از شروع، داستان، توضیحات، قوانین، شرایط سنی در صورت نیاز، تجهیزات لازم، مدت، محدوده، نکات ایمنی، نحوه استفاده از GPS/QR/دوربین و شرایط دسترسی نمایش داده شود. شروع بازی نیازمند پذیرش قوانین و مجوزهای لازم است.

## ۵.۵ محیط اجرای بازی

- رابط موبایل‌محور، فارسی و RTL.
- نمایش عنوان مرحله، شرح مأموریت، رسانه، وضعیت فعلی و پیشرفت.
- نمایش ابزارهای اختصاص داده‌شده به همان مرحله؛ ابزار غیرمرتبط نباید بی‌دلیل نمایش داده شود.
- نمایش پیام‌های موفقیت، خطا، تلاش مجدد و راهنمای مجوز دستگاه.
- نمایش تایمر، امتیاز و مسیر در صورت فعال بودن در تنظیمات بازی.
- ذخیره امن نشست و امکان ادامه پس از خروج یا بسته شدن مرورگر.
- پشتیبانی از اجرای تمام‌صفحه موبایل در صورت امکان مرورگر.

## ۵.۶ نتیجه بازی

سرور نتیجه نهایی را تعیین می‌کند. صفحه نتیجه شامل وضعیت تکمیل، امتیاز، مدت، مراحل تکمیل‌شده، هینت‌های مصرف‌شده، مدال/دستاورد، رتبه در صورت مجاز بودن و امکان ارسال نظر باشد.

# ۶. شهرها و کاتالوگ بازی‌ها

## ۶.۱ مدل City

اگر مدل معادل در مخزن وجود ندارد، مدل City با حداقل مشخصات زیر اضافه شود:

- `id`, `slug`, `name`, `country`, `region`.
- `description`, `cover_image`.
- `center_latitude`, `center_longitude`.
- `boundary` یا محدوده جغرافیایی اختیاری با PostGIS.
- `timezone` بر اساس منطقه زمانی واقعی شهر.
- `language/default_locale` اختیاری.
- `is_active`, `created_at`, `updated_at`.
- مدیران/طراحان مجاز آن شهر.

نام و توضیحات باید قابلیت ترجمه داشته باشند. مختصات باید در بازه معتبر باشند.

## ۶.۲ اتصال Game به City

- هر بازی عمومی در نسخه MVP به یک شهر اصلی تعلق دارد.
- برای کمپین‌های آینده امکان بازی چندشهری/مسیر بین‌شهری در مدل پیش‌بینی شود، اما اجرای آن در MVP الزامی نیست.
- اگر Gameهای قبلی وجود دارند، migration باید بدون حذف آن‌ها انجام شود. رکوردهای قدیمی به شهر «تخصیص‌نیافته» یا وضعیت مهاجرت کنترل‌شده منتقل شوند؛ تا زمان انتساب توسط مدیر در فهرست عمومی شهرها/بازی‌ها نمایش داده نشوند.
- slugهای موجود حفظ شوند؛ قید یکتایی فعلی بی‌دلیل شکسته نشود.

## ۶.۳ وضعیت بازی

وضعیت‌های قابل استفاده در گردش کار:

- Draft: پیش‌نویس.
- Designing: در حال طراحی.
- Testing: نسخه آزمایشی.
- Published: منتشرشده و قابل دسترسی.
- Paused: شروع نشست جدید موقتاً متوقف است.
- Archived: بایگانی‌شده و خارج از فهرست عمومی.

سیاست بازی‌های در حال اجرا هنگام Pause یا Archive باید قابل تنظیم باشد: ادامه نشست موجود، توقف کنترل‌شده یا پایان با پیام مناسب.

# ۷. Game Builder بصری و طراحی جزءبه‌جزء

## ۷.۱ اصل طراحی

Builder فعلی Hive و نقشه گرافی Activity باید حفظ شود و به یک محیط فارسی، واضح و مناسب طراح غیر فنی توسعه یابد. طراحی بازی باید از داخل پنل و در چند گام مشخص انجام شود. طراح نباید برای افزودن مرحله یا انتخاب ابزار نیاز به نوشتن کد داشته باشد.

## ۷.۲ ساختار رابط Builder

سه ناحیه اصلی:

1. **کتابخانه اجزا و ابزارها:** فهرست بلوک‌های محتوا، InteractionCardها، ابزارها، شرط‌ها، هینت‌ها و پایان‌ها.
2. **بوم گرافی بازی:** نمایش مرحله‌ها به‌صورت Node و مسیرها به‌صورت Edge؛ جابه‌جایی، اتصال، بزرگ‌نمایی، مرتب‌سازی و انتخاب.
3. **پنل ویژگی‌ها:** تنظیمات جزء انتخاب‌شده با فرم‌های پویا و اعتبارسنجی.

در موبایل، همین قابلیت‌ها در قالب تب‌ها/Drawer قابل استفاده باشند؛ اما طراحی اصلی Builder برای دسکتاپ بهینه شود.

## ۷.۳ جریان ساخت بازی

1. انتخاب شهر و ایجاد بازی.
2. تکمیل اطلاعات عمومی، داستان، تصویر و قوانین.
3. انتخاب نوع بازی و مدل اجرا (انفرادی/گروهی).
4. افزودن مرحله شروع.
5. افزودن مرحله‌ها به‌ترتیب یا ساخت مسیرهای شاخه‌ای.
6. افزودن محتوای هر مرحله: متن، تصویر، صوت، ویدیو و دستورالعمل.
7. افزودن یک یا چند ابزار از کتابخانه به همان مرحله.
8. پیکربندی ابزار با فرم اختصاصی.
9. تعریف هینت و شرایط موفقیت/شکست.
10. اتصال خروجی مرحله به مرحله بعد یا پایان‌های مختلف.
11. ذخیره پیش‌نویس، اعتبارسنجی، اجرای آزمایشی و انتشار.

## ۷.۴ عملیات روی مرحله‌ها و گراف

- افزودن، حذف، کپی، تغییر نام و جابه‌جایی مرحله.
- اتصال/قطع مسیر بین مرحله‌ها.
- پشتیبانی از چند خروجی برای یک مرحله.
- تعیین اولویت مسیرها و شرط هر مسیر.
- مرحله اختیاری، مخفی، زمان‌دار و مرحله پایانی.
- گروه‌بندی مرحله‌ها در فصل/بخش برای بازی‌های بلند.
- undo/redo، ذخیره خودکار و نمایش وضعیت ذخیره.
- امکان پیش‌نمایش گراف در کنار فرم مرحله.
- اعتبارسنجی چرخه‌ها و جلوگیری از حلقه بی‌نهایت.
- خطاها و هشدارها به مرحله مربوط لینک شوند.

## ۷.۵ ساختار یک مرحله

هر مرحله می‌تواند شامل این اجزا باشد:

- شناسه داخلی ثابت و عنوان نمایشی.
- متن، داستان و دستورالعمل.
- رسانه‌های پیوست.
- یک یا چند InteractionCard/Tool Instance.
- هینت‌ها با ترتیب و سیاست آزادسازی.
- شرط شروع/ورود.
- شرط تکمیل/موفقیت.
- شرط شکست/انقضا.
- امتیاز پایه و قواعد پاداش/جریمه.
- محدودیت زمان و تعداد تلاش.
- مسیرهای خروجی و شرط انتخاب مسیر.
- تنظیمات ایمنی/مجوزهای دستگاه.

در حد امکان ساختار فعلی Dialog Engine و GameVersion.definition استفاده شود؛ مدل Stage جدید فقط در صورت اثبات نیاز مستقل ساخته شود.

## ۷.۶ فرم‌های پویا برای کارت‌ها

- هر InteractionCard باید metadata/schema معتبر داشته باشد تا Builder فیلدهای تنظیمات آن را بسازد.
- نوع داده فیلد: متن، عدد، مختصات، شعاع، انتخابی، چندانتخابی، تصویر، فایل، checkbox، مدت زمان، رنگ و گزینه‌های پیشرفته.
- فیلدها باید عنوان فارسی، راهنمای کوتاه، مقدار پیش‌فرض، محدودیت و اعتبارسنجی داشته باشند.
- طراح فقط پارامترهای مجاز را تغییر دهد؛ کد Python/JavaScript کارت در اختیار طراح معمولی نباشد.
- نمونه تنظیمات باید در حالت پیش‌نمایش قابل مشاهده باشد.

## ۷.۷ اعتبارسنجی قبل از انتشار

انتشار باید در موارد زیر متوقف شود:

- مرحله شروع وجود ندارد.
- مرحله یا شناسه تکراری است.
- گرهی به مقصد ناموجود متصل است.
- ابزار نصب/فعال نیست یا schema ناقص دارد.
- مسیر خروجی مرحله غیرقابل دسترس است.
- پایان موفقیت یا پایان مجاز تعریف نشده است.
- پاسخ یا شرط لازم ناقص است.
- رسانه مفقود/غیرمجاز وجود دارد.
- حلقه بدون سقف یا شرط خروج وجود دارد.
- شرط‌های مسیر متناقض یا غیرقابل ارزیابی هستند.

# ۸. کتابخانه ابزارها و کارت‌های تعاملی

## ۸.۱ معماری افزونه

از InteractionCard فعلی به‌عنوان پایه معماری پلاگین استفاده کن. هر ابزار حداقل سه بخش دارد:

1. metadata/schema برای تنظیمات Builder.
2. پیاده‌سازی رابط کاربر (client implementation) برای نمایش/دریافت ورودی.
3. منطق server-side برای اعتبارسنجی و تولید نتیجه/عملیات.

کارت باید شناسه ثابت، نسخه، دسته‌بندی، توضیح، وضعیت فعال، سازگاری با نسخه موتور و سیاست امنیتی داشته باشد.

## ۸.۲ دسته‌بندی ابزارها

| دسته | ابزارها |
|---|---|
| مکان و جهت‌یابی | GPS، Geofence، نقشه، مارکر، مسیر، قطب‌نما، فاصله تا هدف |
| شناسایی و ورود | QR Scanner، QR Generator، کد اختصاصی، NFC در آینده |
| ورودی و معما | پاسخ متنی، چهارگزینه‌ای، چندانتخابی، درست/نادرست، رمز/کد |
| رسانه | متن، تصویر، ویدیو، صوت، ضبط صدا، ثبت تصویر مدرک |
| زمان | تایمر، مهلت، آزادسازی خودکار هینت، شرط تأخیر |
| تعامل اجتماعی | رأی‌گیری، پاسخ گروهی، متغیر مشترک، تأیید مدیر |
| داده و API | Data Query، شرط مبتنی بر API شهری، آب‌وهوا/رویدادها در صورت پیکربندی |
| امتیاز و پیشرفت | ثبت امتیاز، نشان، پاداش، جریمه، جدول رتبه‌بندی |

## ۸.۳ ابزار GPS و Geofence

تنظیمات Builder:

- نقطه هدف (Latitude/Longitude) یا محدوده چندضلعی.
- شعاع مجاز بر حسب متر.
- حداقل دقت قابل قبول (accuracy).
- تعداد نمونه مکانی موردنیاز.
- حداقل مدت حضور در محدوده.
- حداکثر سن نمونه مکانی.
- پیام نزدیک‌شدن، ورود، خروج و خطا.
- امکان مخفی نگه داشتن مختصات هدف از کلاینت.
- روش جایگزین برای دستگاه/مرورگر ناسازگار.

رفتار: مرورگر موقعیت را با اجازه کاربر دریافت می‌کند و payload را به سرور می‌فرستد. سرور فاصله، دقت، تازگی و تعداد نمونه‌ها را ارزیابی می‌کند. صرف ارسال `inside_radius=true` قابل قبول نیست.

## ۸.۴ ابزار نقشه

- انتخاب provider از تنظیمات سرور؛ گزینه ترجیحی قابل پیکربندی مانند OpenStreetMap/Leaflet.
- نمایش مرکز، محدوده، مارکرهای عمومی و مسیر مجاز.
- سطح زوم و نوع نمایش قابل تنظیم.
- اهداف مخفی یا نقاط آینده نباید پیش از زمان مجاز به کلاینت افشا شوند.
- نبود کلید API نباید باعث شکست کامل سامانه شود؛ provider جایگزین مستند شود.

## ۸.۵ ابزار قطب‌نما

- استفاده از قابلیت Device Orientation مرورگر در دستگاه‌های سازگار.
- درخواست مجوز صریح در مرورگرهایی که نیاز دارند.
- نمایش جهت نسبی به هدف فقط در مرحله مجاز.
- مدیریت کالیبراسیون و خطای سنسور.
- اگر سخت‌افزار یا مرورگر پشتیبانی نکرد، پیام فارسی و جایگزین نقشه/GPS ارائه شود.
- قطب‌نما نباید ابزار اعتبارسنجی نهایی سرور باشد؛ فقط راهنمای سمت کلاینت است.

## ۸.۶ QR Scanner و QR Generator

- اسکن با دوربین و مجوز امن HTTPS.
- تولید کد اختصاصی برای بازی/مرحله/چالش.
- توکن QR باید غیرقابل حدس و ترجیحاً امضاشده باشد؛ پاسخ محرمانه خام داخل QR قرار نگیرد.
- پشتیبانی از یک‌بارمصرف، چندبارمصرف، محدودیت زمانی و محدودیت نشست.
- جلوگیری از استفاده مجدد غیرمجاز و ثبت زمان/کاربر/نشست.
- امکان ساخت خروجی چاپی برای مدیر.
- پیام خطای کد نامعتبر، منقضی، استفاده‌شده یا متعلق به بازی دیگر.

## ۸.۷ ابزارهای پاسخ و رسانه

- پاسخ متنی با نرمال‌سازی فارسی، ی/ي، ک/ك، فاصله‌ها و نیم‌فاصله طبق تنظیم مرحله.
- سؤال چندگزینه‌ای و چندانتخابی با پاسخ صحیح محرمانه در سرور.
- ثبت عکس/ویدیو/صوت با محدودیت حجم، نوع و زمان.
- امکان بررسی خودکار یا صف تأیید دستی.
- فایل‌ها با نام/مسیر امن و URL امضاشده ذخیره شوند.

## ۸.۸ سیستم هینت

برای هر مرحله چند هینت قابل تعریف باشد:

- عنوان، محتوا، تصویر/صوت/ویدیو.
- ترتیب نمایش.
- آزادسازی پس از زمان مشخص یا تعداد تلاش.
- رایگان یا دارای هزینه امتیاز.
- حداکثر تعداد استفاده.
- قفل/باز شدن بر اساس شرط.
- هینت نهایی/نمایش پاسخ در صورت اجازه مدیر.

سرور باید پیش از ارائه هینت، نشست، مرحله، زمان، تعداد و موجودی امتیاز را بررسی کند. کسر امتیاز و ثبت مصرف باید اتمیک باشد.

# ۹. موتور اجرای بازی سمت سرور

## ۹.۱ مسئولیت

موتور بازی در سرور اجرا می‌شود و از Dialog Engine موجود و مدل‌های GameVersion/Session/StateVariable استفاده می‌کند. کلاینت فقط ورودی کاربر و داده خام ابزار را می‌فرستد. سرور تصمیم می‌گیرد چه اتفاقی رخ دهد.

مسئولیت‌ها:

- بارگذاری نسخه مشخص بازی.
- ایجاد/بازیابی Session.
- تعیین مرحله و مسیر فعال.
- ارائه محتوای مجاز همان مرحله.
- اعتبارسنجی ورودی‌ها و فراخوانی کد ارزیاب کارت‌ها.
- کنترل تلاش، زمان، هینت، امتیاز و محدودیت‌ها.
- ثبت رویداد و تغییر متغیرها.
- انتقال به مرحله بعد یا پایان.
- مدیریت توقف، انصراف، شکست و انقضا.
- جلوگیری از درخواست تکراری و race condition.

## ۹.۲ جریان پردازش ورودی

1. کلاینت یک درخواست رویداد با شناسه یکتا، نشست، مرحله و شناسه ابزار می‌فرستد.
2. سرور احراز هویت، مالکیت نشست، فعال بودن نسخه، وضعیت و مجاز بودن ابزار را بررسی می‌کند.
3. تکراری نبودن رویداد و ترتیب مجاز بررسی می‌شود.
4. payload با schema کارت اعتبارسنجی می‌شود.
5. منطق سمت سرور کارت و Dialog Engine اجرا می‌شود.
6. تغییر وضعیت، متغیر، امتیاز و لاگ در تراکنش ثبت می‌شود.
7. پاسخ امن شامل وضعیت تأییدشده و محتوای مجاز مرحله بعد برگردانده می‌شود.

## ۹.۳ حالت‌های نشست

حداقل حالت‌های منطقی: Created، Active، WaitingInput، WaitingReview، Paused، Completed، Failed، Abandoned و Expired. در صورت وجود معادل در Session/engine فعلی از همان استفاده شود و enum موازی بی‌دلیل ایجاد نشود.

## ۹.۴ امنیت منطق کارت‌ها

- طراح بازی عادی اجازه واردکردن یا اجرای کد آزاد Python/JavaScript ندارد.
- کد `entry_actions`، `evaluate_function` و `client_implementation` فقط از مخزن کارت مورد اعتماد، کد داخلی تأییدشده یا نقش فنی مجاز نصب شود.
- به‌روزرسانی کارت از remote repository باید hash/signature را بررسی کند؛ نسخه قبلی قابل rollback باشد.
- metadata و schema کارت از کد اجرایی جدا شوند.
- کارت غیرفعال نباید در بازی جدید انتخاب شود؛ بازی‌های قدیمی با کارت غیرفعال باید هشدار و سیاست سازگاری مشخص داشته باشند.
- ورودی کاربر، پاسخ پیام‌رسان و payload ابزار هرگز به‌عنوان کد اجرا نشود.

## ۹.۵ محرمانگی تعریف بازی

پاسخ صحیح سؤال، مختصات مخفی، token QR، شاخه‌های قفل‌شده، داده حساس و تنظیمات محرمانه کارت نباید در manifest عمومی بازی یا HTML/JS ارسالی به کلاینت قرار گیرد. API باید فقط public configuration لازم برای اجرای رابط را برگرداند.

# ۱۰. نسخه‌بندی و انتشار

- مفهوم `GameVersion` فعلی حفظ شود.
- نسخه منتشرشده باید snapshot پایدار از تعریف، کارت‌ها، تنظیمات و قواعد امتیازدهی داشته باشد.
- ویرایش بازی منتشرشده باید پیش‌نویس/نسخه جدید بسازد؛ نسخه منتشرشده قبلی بی‌صدا تغییر نکند.
- هر Session به شناسه نسخه مشخص متصل بماند.
- قبل از انتشار، اعتبارسنجی خودکار و تست ضروری باشد.
- مدیر مجاز بتواند انتشار را انجام دهد و در صورت مشکل به نسخه قبلی بازگردد.
- هنگام انتشار، سیاست نشست‌های قبلی مشخص باشد: ادامه روی نسخه شروع‌شده یا توقف کنترل‌شده؛ انتقال خودکار نشست به نسخه جدید ممنوع مگر مهاجرت صریح و تست‌شده.
- شماره نسخه، سازنده، زمان، تغییرات و checksum تعریف بازی ذخیره شود.

# ۱۱. امتیاز، دستاورد و تیم

## ۱۱.۱ امتیازدهی

امکان پیکربندی امتیاز پایه مرحله، پاسخ صحیح، سرعت، تکمیل بازی، مصرف هینت، تلاش ناموفق و مأموریت ویژه فراهم شود. تمام محاسبات سمت سرور و به‌صورت قابل ممیزی انجام شود. تغییر فرمول روی نشست نسخه قبلی اثر نگذارد.

# ۱۲. نسخه PWA و قابلیت‌های موبایل

- اپ بازیکن باید به شکل PWA قابل نصب روی موبایل باشد.
- مسیر اپ بازیکن از پنل مدیریت جدا و دسترسی‌های آن محدود باشد.

- در قطع اینترنت، فقط ورودی‌هایی که از نظر قواعد بازی قابل صف‌بندی هستند در IndexedDB ذخیره شوند؛ با شناسه یکتا و وضعیت Pending.
- پس از اتصال، سرور مجدداً آن‌ها را ارزیابی کند؛ UI تا دریافت تأیید سرور وضعیت را «در انتظار تأیید» نشان دهد.
- GPS، دوربین و جهت‌یابی در HTTPS و با اجازه کاربر اجرا شوند.
- اگر قابلیت دستگاه پشتیبانی نشد، جایگزین یا پیام روشن نمایش داده شود.
- نصب PWA نباید وابسته به Telegram باشد؛ Telegram Mini App می‌تواند کانال ورود آینده باشد، نه الزام نسخه اول.

# ۱۸. مدل داده و مهاجرت پیشنهادی

مدل‌های فعلی حفظ می‌شوند. موارد زیر افزوده یا توسعه داده می‌شوند، فقط پس از بررسی دقیق schema فعلی:

| موجودیت | تصمیم |
|---|---|
| City | افزودن در صورت نبود معادل؛ شهرها و محدوده مکانی |

| Session | حفظ موتور و اتصال به GameVersion؛ تکمیل وضعیت مرورگر/گروه در صورت نیاز |
| SessionEvent | افزودن در صورت ناکافی بودن log فعلی برای idempotency و رویدادهای وب |

| CityMembership / scoped permission | ترجیحاً استفاده از Group/Permission فعلی؛ جدول اضافی فقط در صورت نیاز |

## ۱۸.۱ قواعد Migration

- backup قبل از هر migration ساختاری.
- migrationها کوچک، قابل rollback و تست‌شده باشند.
- داده‌های قدیمی Game/Player/Session حفظ شوند.
- برای Gameهای قدیمی بدون City، مسیر انتساب مدیریتی تعریف شود.
- migration نباید همه بازی‌های قبلی را به‌طور خودکار منتشر کند.
- پس از migration، تعداد رکوردهای قبل و بعد تطبیق داده شود.
- migration در CI روی دیتابیس تمیز و دیتابیس دارای داده قبلی تست شود.

# ۱۹. API و قراردادهای وب

قبل از ایجاد API جدید، مسیرهای فعلی Builder، Dialog و Integration را بررسی کن. API جدید باید با الگوی موجود سازگار باشد. endpointهای مفهومی زیر موردنیازند:

| عملیات | مسیر پیشنهادی مفهومی | توضیح |
|---|---|---|
| فهرست شهرها | `GET /api/v1/cities` | فقط شهرهای دارای بازی فعال و قابل مشاهده |
| بازی‌های شهر | `GET /api/v1/cities/{city_id}/games` | بازی‌های منتشرشده شهر انتخابی |
| جزئیات بازی | `GET /api/v1/games/{game_id}` | اطلاعات عمومی، قوانین و شرایط |
| شروع بازی | `POST /api/v1/games/{game_id}/sessions` | بررسی ظرفیت/قوانین و ساخت نشست |
| وضعیت نشست | `GET /api/v1/sessions/{session_id}` | دریافت مرحله و وضعیت مجاز |
| رویداد بازی | `POST /api/v1/sessions/{session_id}/events` | ارسال ورودی ابزار و پاسخ |
| مصرف هینت | `POST /api/v1/sessions/{session_id}/hints/{hint_id}` | بررسی و ثبت هینت در سرور |
| خروج/ترک | `POST /api/v1/sessions/{session_id}/abandon` | تغییر کنترل‌شده وضعیت نشست |
| شهرهای مدیر | `/admin/cities/` | CRUD شهر بر اساس مجوز |
| مدیریت بازی | `/admin/games/` | CRUD و کاتالوگ |
| ذخیره پیش‌نویس | `/admin/games/{id}/draft/` | ذخیره تعریف Builder |
| اعتبارسنجی گراف | `/admin/versions/{id}/validate/` | کنترل ساختار، کارت‌ها و مسیرها |
| انتشار | `/admin/versions/{id}/publish/` | انتشار نسخه معتبر |

این مسیرها قرارداد مفهومی‌اند؛ از مسیرهای موجود استفاده یا آن‌ها را با حفظ backward compatibility تکمیل کن. فقط در صورت نیاز واقعی URLهای جدید اضافه کن.

# ۲۱. برنامه توسعه مرحله‌ای

| فاز | محدوده | تحویل‌دادنی و معیار پایان |
|---|---|---|
| ۰ | ممیزی مخزن و تست baseline | چهار سند audit؛ نصب submoduleها؛ گزارش تست فعلی؛ بدون تغییر عملکردی |
| ۱ | فارسی‌سازی و RTL پایه | locale فارسی، راست‌چین صفحات موجود، انتخاب زبان، تست صفحات مدیریت |
| ۲ | City و کاتالوگ چندشهری | مدل شهر، اتصال بازی‌ها، migration امن، صفحه انتخاب شهر و بازی‌های شهر |
| ۳ | حساب بازیکن و PWA پایه | اتصال User به Player، ورود، پروفایل، manifest/service worker و صفحه عمومی |
| ۴ | اتصال PWA به موتور موجود | ایجاد نشست و ارسال رویداد وب به Dialog Engine؛ ادامه بازی پس از reload |
| ۵ | Game Builder ارتقایافته | طراحی مرحله‌ها، ابزارهای قابل انتخاب، فرم پویا، ذخیره و validation |
| ۶ | ابزارهای مکانی و ورودی | GPS، Map، QR، Compass، Timer، Quiz، Text و Media به شکل کارت |
| ۷ | هینت و امتیاز | زمان‌بندی هینت، هزینه، score ledger در صورت نیاز، گزارش تکمیل |
| ۸ | نسخه‌بندی و انتشار | draft/test/publish، قفل نسخه، rollback و حفظ نشست‌های قدیمی |
| ۹ | گروه و تیم | دعوت، عضویت، امتیاز تیمی و realtime در محدوده مصوب |

پس از هر فاز، کاربر باید بتواند خروجی همان فاز را آزمایش کند. توسعه را یک‌باره و بدون نقاط کنترل انجام نده.

# ۲۲. معیارهای پذیرش نهایی

سامانه زمانی قابل قبول است که:

1. تمام صفحات اصلی مدیریتی و کاربری فارسی و RTL باشند و انگلیسی‌سازی ساختاری حفظ شود.
2. مدیر بتواند شهر بسازد، ویرایش کند و فعال/غیرفعال کند.
3. مدیر بتواند چند بازی مستقل در یک شهر بسازد.
4. کاربر پس از ورود ابتدا شهرها را ببیند و فقط بعد از انتخاب شهر، بازی‌های همان شهر را مشاهده کند.
5. مدیر بتواند بازی را با Builder گرافی و جزءبه‌جزء طراحی کند.
6. طراح بتواند برای هر مرحله چند کارت/ابزار اضافه و هرکدام را از طریق فرم تنظیم کند.
7. تغییر تنظیمات کارت بدون تغییر کد ابزار امکان‌پذیر باشد.
8. گراف خطی و شاخه‌ای به‌درستی اجرا شود.
9. موتور سرور از Dialog Engine موجود استفاده کند و مرجع نهایی وضعیت بازی باشد.
10. کاربر بتواند از PWA بازی را شروع و پس از بستن/بازکردن مرورگر ادامه دهد.
11. GPS، QR و ابزارهای فعال هر مرحله در مرورگر موبایل به‌درستی کار کنند یا محدودیت دستگاه را دقیق توضیح دهند.
12. هینت‌ها طبق زمان/تعداد/امتیاز آزاد شوند و مصرف تکراری باعث کسر امتیاز دوباره نشود.
13. نسخه منتشرشده تغییرناپذیر بماند و نشست‌های قدیمی از نسخه خود استفاده کنند.
14. اطلاعات پاسخ صحیح و secretهای کارت در payload عمومی افشا نشوند.
15. migration داده‌های قبلی را حفظ کند و تست آن موفق باشد.
16. Docker در محیط مستندشده از ابتدا تا انتها بالا بیاید و داده‌ها در volume پایدار بمانند.
17. قابلیت‌های موجود Hive که پیش از توسعه کار می‌کردند پس از تغییرات نیز تست شوند.
