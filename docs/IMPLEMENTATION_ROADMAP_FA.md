# نقشه راه پیاده‌سازی Hive Mechanic بر مبنای SRS

این نقشه راه بر حفظ Django، موتور `django_dialog_engine`، مدل‌های فعلی و تمام Submoduleها بنا شده است. هر فاز مستقل، قابل تست و قابل بازگشت است. تا پایان فازهای پایه، هیچ بازنویسی موتور یا تغییر فناوری اصلی پیشنهاد نمی‌شود.

- Docker و Docker Compose روی سیستم نصب/در PATH نیستند؛ مسیر Docker قابل اجرا نبود.
- برای تولید، PostgreSQL + PostGIS انتخاب مناسب است؛ برای تست مستقل Windows، SQLite معمولی عملی‌تر است، اما Django Check واقعی هنوز اجرا نشده است.
- compileall برای `builder` و Migrationهای `0050` تا `0055`: موفق.
- تست مستقل `builder.tests.tests_urban_tools`: موفق، ۲ تست.
- تست discovery کامل Builder: ناموفق؛ علت‌ها نبود Django، selenium و six و اجرای مستقیم یک تست relative-import خارج از package است.
- `manage.py check`، Migrationها، تست‌های ORM، Selenium، PWA، PostgreSQL/PostGIS و End-to-End اجرا نشده‌اند و موفق اعلام نمی‌شوند.
- هیچ دیتابیس واقعی یا اطلاعات کاربر لمس نشده است.

## تصمیم‌های فناوری و دلیل فنی

### Django و Dialog Engine

حفظ می‌شوند؛ چون مدل، migration، Card Repository، CLI، کانال‌ها و تست‌ها به آن‌ها متصل‌اند. جایگزینی، مهاجرت داده و بازتولید semantics موتور را هم‌زمان تحمیل می‌کند و برای SRS ارزش مستقیمی ایجاد نمی‌کند.

### PostgreSQL/PostGIS

برای تولید توصیه می‌شود، نه به‌عنوان بازنویسی فوری. City boundary، geofence، index مکانی و query هم‌زمان به قابلیت‌های GIS نیاز دارند. ابتدا migration و backup/restore روی snapshot آزمایش شود؛ SQLite می‌تواند برای تست محدود باقی بماند.

### PWA به‌جای اپ native

برای MVP کافی و کم‌ریسک‌تر است چون یک مسیر وب را حفظ می‌کند، اما باید service worker، IndexedDB، HTTPS و fallback واقعی پیاده شود. Telegram Mini App یا native نباید پیش از اثبات نیاز جایگزین مسیر اصلی شود.

### API جدید

تنها برای مرز عمومی بازیکن و قرارداد event اضافه شود؛ endpointهای داخلی Builder بازنویسی نشوند. نسخه‌گذاری و backward compatibility از شکستن کانال‌های موجود جلوگیری می‌کند.

## معیار آماده‌بودن برای انتشار MVP
